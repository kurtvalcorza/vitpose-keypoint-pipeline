## Conformance notes

- **Standalone carrier (NOTEBOOK_SPEC 2.0 §4):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/vitpose_keypoint_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the shared weights root working-directory-relative), Section 3 carries **both** model identities and both SHA-256 manifests inline (`MANIFEST` for ViTPose, `DETECTOR_MANIFEST` for RT-DETR) and asserts each agrees with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the generating revision, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR3):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, either inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition (MOD1–MOD8):** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` and `stage_missing_detector_files(DETECTOR_WEIGHTS_DIR, allow_download=True)` fetch only the manifest entries that are absent, from the Hugging Face Hub at the immutable revisions (never `main`); `verify_snapshot` and `verify_detector_snapshot` re-hash every entry; `from_pretrained(weights_dir=WEIGHTS_DIR, detector_dir=DETECTOR_WEIGHTS_DIR)` loads both verified directories with `local_files_only=True`, `trust_remote_code=False` and, for the detector, `use_pretrained_backbone=False`. The notebook's only external dependencies are the pinned PyPI distributions and the Hub at those two revisions.
- **Role stages:** `validate_inputs` writes `outputs/vitpose_keypoint_input_manifest.json` with the schema (17 keypoint names, both models' preprocessing), the ceilings, the input's observed mode and size, the boxes and their source, both thresholds, the verdict, both identities, and one recorded rejection finding from the box-outside-image probe; `evaluation_report` writes `outputs/vitpose_keypoint_evaluation_report.json` — `sample-sanity` with one `keypoint_pck` entry per person (correct/total within the PCK radius, mean pixel error) on the synthetic drawing, plus the stage-1 finding; `not-measurable` on BYOD (with what labelled data would make the task measurable).
- The default sample is a deterministic 640×640 cartoon person drawn in code with Pillow from 17 joint coordinates (no text rendering, so its digest is stable across Pillow builds) — the same drawing the smoke run used; `keypoint_pck` against joints you drew yourself, inside a box you supplied, is sanity evidence for the input contract, the affine crop, the forward pass and the coordinate mapping, not a pose metric. **Stage 1 on this drawing is a recorded finding, not a measurement:** the photograph-trained detector returns no `person` at the default threshold (seven low-confidence proposals at 0.05 in the smoke run), so the notebook hands the drawn box to stage 2 and says so.
- Score semantics (UNC1–UNC4): every keypoint `score` is the joint's heatmap maximum after the affine warp, not a calibrated probability; the detector's `person_score` is RT-DETR's per-class sigmoid; the notebook states that a box without a person still yields 17 low-scoring joints. Both thresholds are caller-owned request parameters exposed as `# @param` values with the package defaults 0.3/0.3 (the pinned ViTPose README example's values, not a calibration) and passed explicitly on every call; `keypoint_pck` scores all 17 predicted joints regardless of `keypoint_threshold`. The notebook performs no validation of its own — image, boxes and thresholds are checked only by the pipeline's `validate_inputs`/`estimate` path.
- Ceilings `MIN_IMAGE_SIDE` (16), `MAX_IMAGE_SIDE` (4096), `MAX_PERSONS` (50), `DETECTION_THRESHOLD`, `KEYPOINT_THRESHOLD`, the 17 `KEYPOINT_NAMES` and `PCK_FRACTION` (0.1) are printed before the models run.
- CPU is documented as adequate (card-measured 0.3 s for stage 1 on the 640×640 drawing, 0.15 s for stage 2 on one person; 17/17 joints at scores 0.85–0.97, mean error 12.8 px, PCK 1.0 within the 48 px radius).
- `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
